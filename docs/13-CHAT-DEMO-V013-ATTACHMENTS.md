# chat-demo v0.1.3 附件变更评估

> 这是对官方 v0.1.3 附件相关代码的增量审阅，不替换 `docs/evidence/chat-demo/` 中固定于 v0.1.2 的源码快照。Release 于 2026-11-20 发布，标签指向 commit `8ad7b56e196b87d8a3215dc09476d6d146ad3f0e`。文件级 Git blob 标识见 `docs/evidence/chat-demo/SUPPLEMENTAL-v0.1.3.json`。

## 结论

对本项目有直接帮助。可复用的核心不是新的消息协议，而是图片尺寸规范化和 `file_id` 生命周期管理：图片长边超过 4096 像素时，生成等比例缩小的**上传副本**；旧历史中的超限图片在发送前重新检查，命中时清除旧 `file_id`，复用本地原图走现有补传链路。原始本地附件不被覆盖。

## v0.1.3 观察到的行为

- `resizeUploadImage.ts` 先解码本地图片，再以 `4096 / 长边` 等比缩放；像素尺寸四舍五入，短边至少为 1 像素。
- JPEG、WebP 尽量沿用编码类型，其他格式使用 PNG；编码结果格式变化时，上传文件名后缀跟随真实 MIME。画布编码质量参数为 `1`。
- 这条浏览器实现用 `Image` 与 Canvas；动图画布化时只绘制一帧。若移植到原生平台，必须明确动图策略，不要把“保留原件”误做成“服务端仍收到动图”。
- 新增的 `imageSizeChecked` 是对**当前 serverId 所对应上传图**的检查标记，不是“本地原图已缩小”的标记。上传成功后，只有图片才记录检查完成。
- 发送时，旧消息里缺少检查标记的图片会读取本地原件并检测尺寸；超限时清掉 serverId，交给同一套本地附件补传逻辑。原件无法读取时不把“未知”伪装成“尺寸合格”。
- 本轮附件上传失败会阻止本轮请求；历史上下文附件补传失败则不阻断新问题，该附件本轮不进入上下文，后续仍可再试。
- 无效 `file_id` 的识别与有限重试已在参考代码中存在；v0.1.3 的新增价值是大图检测能够主动让旧 ID 失效并触发补传，而非无限重试。

## 放进 KMP/MVI 的实现合同

1. **本地原件和服务端 ID 分开管理。** 消息快照只存附件元数据、稳定本地 ID、可空 `serverFileId`、检查版本/标记和尺寸；二进制仍由平台文件存储持有，禁止 Base64 塞进会话 JSON。
2. **UI 上传是状态机，不是按钮回调里的黑盒。** 至少覆盖 `Selected → Validating → Normalizing/Uploading → Ready`，并明确 `Failed/Cancelled`。MVI Action 应携带稳定附件 ID；迟到上传结果不能覆盖已删除附件或新一轮状态。
3. **发送前先准备本轮文件，再构造请求。** 图片与文档分别映射 `image` / `document` 内容块；没有本地原件又没有可用服务端 ID 时只展示不可发送附件，不能发空引用。
4. **上传和聊天错误分层。** 当前问题文件上传失败应呈现可重试状态且不声称已发送；历史文件重传可降级跳过。服务端明确报告 ID 无效时只重传受影响文件，无法定位具体 ID 时才考虑重传本次请求的附件集合，并设置重试上限。
5. **大图修复应幂等。** 记录“此服务端 ID 对应已规范化图片”，尺寸策略变更时用版本号使旧标记失效；本地原图保持不变。对同一稳定 ID 的并发上传应合并，避免多端/多 Intent 重复产生上传。
6. **按平台实现二进制适配器。** `commonMain` 共享附件状态、校验策略和请求引用；Android/iOS/Web 各自提供安全文件句柄、媒体解码/缩放及 multipart 传输。跨平台先统一长边和错误语义，编码字节级一致性另做实测，不能仅凭 API 类型宣称等价。
7. **Files 能力仍需实测。** 继续遵守 Files beta header 与 `purpose` 字段顺序；文档上传、扩展模式、CORS/权限、真实限制以及 API Key 能力范围不因 v0.1.3 的图像修复而自动得到验证。

## 本项目实现状态

共享层已经落地附件元数据持久化、Files multipart 上传、原图与上传副本分离、发送前补传、有限次失效 `file_id` 重试，以及 981 项官方扩展名清单。Android 使用系统文件选择器、`AtomicFile`、Keystore 和 Bitmap/ImageDecoder；Web 直接复用 chat-demo 的附件卡片 UI，以 IndexedDB 保存原件并由 Canvas 生成上传副本；iOS 使用文件选择器、Application Support、ImageIO 和同一 `NativeClient` 桥。

已用 MockWebServer 验证 multipart 的 `purpose` 位于 `file` 之前、历史大图只重传副本、原图保持不变、服务端报告失效 ID 后只清理对应引用并重试。Web 已在 Chromium 中实际完成“选择文件 -> chat-demo 原版草稿附件卡片 -> 移除”的交互检查，并确认附件状态最终由 KMP 投影驱动。iOS 首次 macOS/Xcode 编译仍由 GitHub Actions 执行，未完成前不能声称双端附件均已通过平台验收。
